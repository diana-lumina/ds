# Releases

Historial de cambios del Design System. Seguimos [Semantic Versioning](https://semver.org/lang/es/).

---

## Política de versionado

<table>
  <thead>
    <tr>
      <th>Tipo</th>
      <th>Versión</th>
      <th>Cuándo</th>
      <th>Ejemplo</th>
    </tr>
  </thead>
  <tbody>
    <tr>
      <td>**Major**</td>
      <td>X.0.0</td>
      <td>Breaking changes, algo deja de funcionar como antes</td>
      <td>Renombrar una prop, cambiar el HTML generado, remover un componente</td>
    </tr>
    <tr>
      <td>**Minor**</td>
      <td>0.X.0</td>
      <td>Nueva funcionalidad retrocompatible</td>
      <td>Nuevo componente, nueva prop opcional, nueva variante</td>
    </tr>
    <tr>
      <td>**Patch**</td>
      <td>0.0.X</td>
      <td>Bug fix o mejora sin cambios en la API</td>
      <td>Fix visual, corrección de accesibilidad, mejora de rendimiento</td>
    </tr>
  </tbody>
</table>

:::tip 
Cómo leer un breaking change
Si al actualizar necesitas cambiar código en tu proyecto, es un **major**. Si no necesitas cambiar nada, es **minor** o **patch**.
:::

---

## Qué esperar en cada release

**Major (X.0.0)**
- Guía de migración incluida
- Período de deprecación previo cuando sea posible
- Comunicación directa a los equipos consumidores

**Minor (0.X.0)**
- Nuevos componentes o variantes listos para usar
- Retrocompatible, no requiere cambios en tu proyecto

**Patch (0.0.X)**
- Correcciones silenciosas
- Seguro actualizar en cualquier momento
